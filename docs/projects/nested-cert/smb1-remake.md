## Verdict: **Jank**

Nested runs the remake's NES code correctly. It reaches gameplay, plays, dies, and comes back with the same lives,
level and timer as the NES. **BrokenNes's SNES core agrees with Mesen** on every poll except NESFab scratch bytes, with
the same lag frames. Two things, both confirmed on Mesen, keep the SNES out of step with the NES:

1. the game logic runs **8 steps behind the NES** from the title until the first death;
2. the DMC-IRQ timing routine never finishes on the SNES (`dmc_stage` stays at 1).

In addition the SNES lags 5-17 frames per 2700-4000 frames.

## Method

Same as [vrun.md](vrun.md): `Workshop --nested-cert`, locked on controller polls, with the same buttons per poll. With
no custom input set, NES A = SNES B and NES B = SNES Y.

Inputs come from the remake's own parity schedules (`source/engine/parity/probe_common.lua`), regenerated by
`BrokenDev/projects/smb1-nested/gen-cert-inputs.py`:

- Start at frames 5-30.
- t=1 is the frame after NES T0, NES frame 203. T0 is when the player has had control for 30 frames, the way
  `ours_probe.lua` defines it.
- **recorded**: the user's own play. `recorded_input.csv` holds button presses only at t=170235-170984, so that window is
  replayed (801 frames).
- **fuzz1-3**: the deterministic fuzz generator, ported 1:1.
- **verify play**: the `smb1-nes` project's script.

## Every difference (NES vs SNES)

1. **`logic_ticks` (`$0795`, the remake's FrameCounter) falls behind on the SNES.** It is 1 behind at poll 6, 8 behind by
   poll 141 (title / WORLD card), and stays 8 behind through 1-1. The camera start (`area_off_start`), `game_timer_ctrl`,
   `game_time` (one tick), `color_rotate_*`, `hb_tick` and the draw rotation (`enemy/misc_draw_first`) all follow from it.
   The state re-converges after the first death (fuzz1 poll ~1600: lives, logic_ticks and the camera are equal again). In
   the recorded run it never re-converges within 4000 frames.
   *Likely cause in the core:* the remake's logic ticks are paced by its NMI hand-off (`nmi_defer`, `nmi_ready`), and
   Nested delivers the NES NMI at the game's idle point rather than at a fixed cycle. While the title and the card run,
   some polls happen without a logic tick on the SNES. The 2-frame lag pairs at 97 and 253/262 sit in exactly that
   window.
   *Effect:* the same input lands 8 game steps later on the SNES. A frame-exact NES replay does not reproduce on the SNES
   (jumps start 8 steps later), although each run is internally correct.
2. **`dmc_stage` (`$0338`) stays 1 on the SNES** from poll ~186 and never returns to 0. `dmc_polls` / `dmc_p2` diverge too.
   *Cause:* Project Nested does not emulate the DMC IRQ. The `dmc_status` post-build patch makes `$4015` bit 4 read 0 so
   that the timing routine does not hang. The routine therefore takes its "no IRQ" path every time.
   *Effect:* no visible one found in these runs (music and SFX state match once the logic phase re-converges). Any
   DMC-IRQ-timed raster or sample effect would be missing.
3. **Music phase**: `mus_wait`, `mus_ptr` and the `mus_shadow_*` registers are off from poll 10, follow item 1, and
   re-align at track changes.
4. **NMI landing and scratch** (`runtime_nmi_saved_*`, NESFab temporaries): expected, no effect.
5. **SNES lag**: 5-17 frames per run, in 2-frame pairs. The feedback build already removed the runtime recompiles (376
   -> 5 in the first 1200 frames). What is left sits at level events: likely Nested's slow paths (PPU/VRAM uploads at
   area changes), not compiles. This was not profiled further this round.

## What an MMC3 build would hit

The remake's MMC3 build (`2026-11-10_acb0047a_mmc3-preview`) was not built or run. From the MMC3 findings
(`Project-Nested-core/Documentation/NestedFork-MMC3-findings.md`):

- Items 1-5 are mapper-independent and would carry over.
- **Step 17 (the atomic PRG-slot write) is not applied to Mapper4.** The remake's MMC3 build makes far calls through
  R6/R7 trampolines (its known lag cost) many times per frame. Each one opens the torn-bank window to an NMI, and on the
  SNES the NMI lands somewhere else every run (item 4). **This is the highest-risk item.**
- The MMC3 IRQ ignores the I flag and is virtual-scanline based. That matters only if the remake uses the MMC3 IRQ (its
  status bar split is sprite-0 based in the original). Not measured.
- `$A001` is not implemented, which is harmless unless the build write-protects the PRG-RAM.

## 2026-11-12 round 2: fixed-time NMI (`-Nmi accurate`)

Core unchanged (step 18); the fixed-time NMI is Project Nested's own `NmiMode.AtVblank` on / `NmiMode.AutoDetect` off,
written per game by `nested-build.ps1 -Nmi accurate` (see vrun.md round 2). The smb1 feedback plans already pressed B/Y;
the project's verify/oracle script was fixed. Feedback re-run, personal builds in the session scratchpad only
(`smb1_nested_personal\`, fast = 0d6471f4..., byte-identical to round 1; accurate = 345a2d77...).

| scenario | SNES lag fast -> accurate | `logic_ticks` behind the NES in 1-1 (poll 600), BrokenNes fast -> accurate (Mesen accurate) |
|---|---|---|
| fuzz1 | 9 -> **2** | 8 -> **6** (7) |
| fuzz2 | 13 -> **2** | 8 -> 6 |
| recorded | 5 -> **2** | 8 -> 6 |

- **The 8-step lag is reduced, not gone (6 steps).** The remake catches up missed NMIs with extra logic ticks during the
  boot/title loading (`logic_ticks` jumps by several per poll on the NES at polls 6-23). How many NMIs elapse during those
  loads depends on how fast the SNES does the loading, not on where the NMI lands, so a fixed NMI time can only remove the
  part caused by late delivery (2 steps). The rest needs the loads to take the NES's number of frames.
- **Lag frames:** the 2-frame lag pairs (97, 253, level events) are gone; 2 single lag frames remain (90, 268).
- **Cross-check:** BrokenNes SNES vs Mesen SNES in accurate mode differ on 2692 of 2696 polls (Mesen ends 7 ticks behind,
  BrokenNes 6): the async NMI exposes their sub-frame timing differences. Fast mode agreed.
- Re-converges after the first death in both modes, as before. `dmc_stage` unchanged (DMC not touched this round).

**Recommendation for SMB1: accurate** (fewer lag frames, smaller step gap), verdict stays **Jank** until the boot-load
catch-up is matched.

## 2026-11-14 round 4: DMC IRQ in the core (fork lane-dmc, step 70)

Core: fork branch `lane-dmc` a6ca856 (on nested-vrun-core b1967c8), profile `universal` step 70, md5 `f04a2545`.
New universal-only step 70 `dmc_irq`, opt-in per game with the injector setting `Cpu.DmcIrq` (SelfMod hooks: games
without it keep step 61's code and timing). SMB1 gets it from `BrokenDev/projects/nested-core/games.json` (`settings`,
read by `nested-build.ps1`, new `-ExtraSettings` too). The `dmc_status` post-build patch is **dropped**: the real model
ends DMC samples, so the arm's sync loop exits by itself (x = 2 polls) and IRQ 1 / IRQ 2 really run.

How the IRQ is timed: end time in NES cycles from the NMI (a start inside the DMC IRQ handler counts from the previous
end; first bit at the old rate: 54 + 8*P1 + 7*P2, the remake's generator formula). In NmiMode.AtVblank Nested has no NES
scanline clock, so the IRQs due are delivered at the NES NMI's return, in order (the handler returns to the same point);
IRQ 2 polls $2002 for sprite 0 and Nested moves its virtual scanline to the sprite-0 line, so the split lands there.

Feedback brokennes as before (m30 106 entry points, MMC3 118). ROMs: `T:\BrokenDev\Releases\Nested_SMB1\2026-11-14_a6ca856`.
