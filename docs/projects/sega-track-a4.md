# Track A4: Master System, Game Gear, SG-1000, round 4 (2026-10-15)

Record of the fourth round on the Z80 consoles. Earlier records: `sega-track-a.md`, `-a2.md`, `-a3.md`. Provenance of code and outside facts: `Windows/NesEmulator/sega/THIRD_PARTY_NOTICES.md` (nothing was ported this round; the oracle, Mesen 2.1.1, was only run, black box, its code never read). Branch `worktree-agent-a314e5c62d8920ea5`, from `main` = `5c974b2`, with `main` (`e758833`) merged in, not pushed. The shared bar is in `sega-tracks-brief.md`, "Round 4 additions".

**Summary.** All 40 roster games (20 Master System, 20 Game Gear) were played with scripted input that reaches gameplay and compared with Mesen frame by frame; the whole of both libraries was swept again and every non-ok game that is not a tagged bad dump or a noisy scene was run against the oracle; sound was compared at the event level (the chips' registers at every frame end); every core slot of both consoles was hot-swapped mid-game through the apps' session; save states were round-tripped on all 40 games; all five battery games were saved by their own save command and restarted from the save, every picture and the cartridge RAM equal to the oracle's in both passes (Shining Force II after a 64,800-frame play with a lost first battle); UAT cases exist and pass. **What is not done:** see "Not tested / open". (Shining Force II's boot-time interrupt difference, which was open in the first version of this record, is explained: the oracle's line counter powers up at 0.) Where the picture differs from the oracle the cause is named below with its evidence; where it is not established it says so. No Z80 or PSG source was changed this round. `SmsVdp.cs` gained two additions that do nothing unless a tool asks for them (the `OracleLineCounterAtPowerOn` setting and a hook that reports colour RAM writes), so the gates that touch the VDP were run again on the final tree (listed under "Verifiers": `--smstest --prove`, `--z80test --selftest`, `--md-test`, `--sega-bridge-test`, the UAT suite and the preview smoke).

### What the remaining differences are

1. **The oracle's Z80 is not the Zilog one** (A2): ten games gain 40 frames or more from the oracle's lengths (Columns Master System 304 to 2,389 and Game Gear 522 to 2,399, Bubble Bobble Master System 1,655 to 2,388, Penguin Land 342 to 2,338, Dragon Crystal 576 to 2,396, Sonic 2 on the Master System 2,355 to 2,399 and on the Game Gear 1,726 to 2,399, Tails' Adventures 2,276 to 3,599, Ristar 2,345 to 2,399, Black Belt 642 to 1,037); the others move by a few frames. The app keeps the manual's table (it passes z80test's hardware CRCs); the lengths are a tool setting. Out Run is the other way round (2,387 by default, 2,371 with the lengths: the lengths are an approximation).
2. **The oracle disagrees with itself** (its power-on line is random and a game's state follows it): **Black Belt** (its two runs differ on 1,758 of 2,399 frames, from frame 151: the same frame at which this emulator first leaves the first run, by 11 to 14 pixels on a few lines while the game clears the name table during the picture; the next frames are equal again, then the games part), **Space Harrier** (2,085 frames from frame 212: of the 314 frames where the oracle's runs agree, 292 are equal, 299 counting the frames equal to one of its runs), **Penguin Land** (the 61 frames left with the oracle's lengths), Ultimate Soccer (Europe) in the library (704 of 1,499). With only one oracle run these games cannot be compared beyond where its runs agree: this is the limit of the comparison, not a verdict on the emulation.
3. **A boot-time difference of one interrupt: Shining Force II (Game Gear), explained: the oracle's line counter powers up at 0.** At the game's first `EI` (`$004B`, after it sets registers 0 to 10 with the display off and never having read the status port) the oracle's line interrupt is already pending (`cpu.activeIrqs` is 1, `vdp.scanlineIrqPending` true with `enableScanlineIrq` true after the write of register 0), and it takes the interrupt after the next instruction; this emulator's is not pending. The oracle's state at the end of each of the first frames shows the flag set in **frame 1** and never cleared (the game does not read status before that `EI`): with no BIOS its line counter latch starts at 0, so it underflows at the first picture line of its first frame (by the model, a power-on line in the blanking lines, 193 or more, would reload the counter first and leave nothing pending: not tried), and the flag stays until the status port is read. A real machine runs its BIOS first, with register 10 at $FF (the registers the first instruction of a cartridge sees are the same in the oracle and here), so the counter is reloaded every frame and cannot underflow: nothing is pending at the first instruction, which is the state this emulator starts in (this is the reasoning, not a measurement on a real console). Evidence: in four oracle runs (power-on lines 115, 130, 75 and 163) the first `$0045` is at frame 15 or 16, line 178, with the line flag pending in all four; this emulator with the same line has it not pending; with the tool setting `--tune OracleLineCounterAtPowerOn=1` (the counter at 0 at power-on, never on in the app) the first run alone is equal to the oracle's on 2,589 of 2,599 frames instead of 2,501, and a 64,800-frame play (the save pass above) is identical at every checkpoint. So the difference is the oracle's (no BIOS), not this emulator's: the app keeps its state, the setting is for comparing games with the oracle.
4. **Colour-RAM dots: Bubble Bobble (Game Gear), 186 frames: taken apart, the rule is only partly found.** Over the 2,398 frames of the roster script (oracle power-on line 109, the oracle's Z80 configuration; 3,141 pixels in 186 frames), with every colour RAM write listed (`--watch-dots`) and the oracle's pictures (`--save-pngs`): **68 frames differ only by single dots the oracle draws for a colour RAM write while the display is ON** (this emulator draws dots only with the display off, and lets a colour written with the display on take effect at its access slot without a dot); 4 more mix such dots with other pixels; 109 frames differ in one to three pixels of the same kind at other offsets; 5 frames (847, 849, 986, 988, 989; 233 to 990 pixels) are another effect: whole lines at the top of the picture (frame 849: lines 0 to 5, all 160 pixels) differ, a display enable at line granularity. What is established: the oracle's dot is at **the pixel the write arrives at plus 2** (117 of the 308 pixels explained by a write of that colour on their line; the others at -14 to -7 and +5 to +8 pixels, where a second write of the same colour on the line cannot be excluded), not at the access slot (the offset from the slot spreads from -45 to +6). What is not: **the oracle shows a dot for only about half of the display-on writes** (110 of 239 writes in the visible window whose colour differs from its neighbours'), and nothing tested separates them: the slot phase of the write, its arrival modulo 2 to 16 master clocks, a first byte still pending, the colour RAM index, the colour, the pixel underneath (backdrop or not); it depends on the row and the stretch of the game (the bottom lines 150 to 167: dots in 80 %; lines 36 to 60: 18 %) and it is not a Z80 timing difference (with the oracle's lengths the cycle counts of the same instruction differ by a constant 1 over the frames). Because the frames differ in one to three pixels at the bottom of the picture, and the rule is half known, **nothing was changed**: drawing a dot for every display-on write would add as many wrong dots as it removes (110 right, 129 wrong in the sample). The tools are kept: `--sms-run --watch-dots a-b` (every colour RAM write with its dot, or -1), `--save-pngs`, `mesen-capture.ps1 -Watch` (the oracle's write instructions with its line, dot and interrupt state).
5. **The data port during the picture: the oracle loses bytes that a block write sends too close together; this emulator keeps them all (new, measured with probes).** `vram-probe.py` writes 64 distinct bytes (or a name table row) through the data port while the picture is drawn, at 41 phases one Z80 cycle apart, and `vram-probe-sweep.ps1` compares what reached VRAM and the picture with the oracle's at the same power-on line. Three write rhythms, 41 phases each: **`OTIR` (a write every 21 cycles): the oracle lost one byte in 25 of the 41 runs and none in the other 16; `OUTI` x 64 (every 16 cycles): 491 bytes over the 41 runs (about 12 each; no run kept all 64); a game's usual `LD A,(HL) / OUT / INC HL` loop (every 24 cycles): none in any**; this emulator keeps all 64 every time. A lost byte is lost entirely: the bytes after it move down by one, the address register does not advance. In this emulator's time base (the line-relative master clock a write arrives at), every `OTIR` byte lost arrived at exactly 191 or 383 (of the arrivals at those two times, all but one were lost; none was lost at 188, 194 or any of the other 2,600 arrivals), and the `OUTI` losses are nearly every arrival in a window of 12 to 15 master clocks that starts just after each multiple of 64 (65 to 77, 129 to 140, 192 to 206, ...). With the pictures: **wherever the oracle accepted every byte, the pictures were identical, 101 of 102 times** (name table row probes of the `OTIR` kind, 6 sweeps; the one exception, equal contents and a different picture, did not come back in the next four sweeps), so when a write takes effect matches; whether it is accepted does not. The rule behind the oracle's losses is not found: a one-write buffer that is emptied at the next access slot and loses what arrives while it is full, searched over the slot position (a periodic grid of 64 clocks at every offset, with the clocks a write needs before a slot can take it from -30 to +70; a per-line grid of 8 slots at 96 to 160, with -20 to +60), strict or loose comparison and the tie rule, never beats "nothing is lost" on the three rhythms together (the per-line grids lose the 24-cycle loop that the oracle does not). Nothing was changed. Black Belt's frame 151 (VRAM identical at the frame's end in both, so not a lost byte) is therefore not of this kind either.
6. **Isolated frames** (1 to 19 per game: a band of lines of a few dozen pixels). Black Belt's frame 151 was taken apart: the game rewrites the name table through the whole frame (1,312 VRAM writes in frame 151), RAM and VRAM are identical at the frame's end, and the picture differs on a few lines, so the effect is a write landing a little earlier or later against the beam. **A scan of every VDP write-slot parameter against the oracle** (slot start 112 to 144 master clocks, period 56 to 72, slots per line 4 to 16, write latency -9 to +40; 12 games, 1,499 frames each, frames equal to the oracle's first run): the default is at the optimum (15,511 frames; no other setting reaches it, the best is 15,506 with a write latency of +3; a slot start of 112 loses 2,389, other settings 5 to 40), and latching each background tile once, with the name-table fetch 0 to 48 pixels ahead of its pixels (tried, then reverted), gains at most 7 frames of 15,500 and does not touch Black Belt's frame. So the difference is not a parameter of the model: it is the VRAM access queue A3 decided not to model. Nothing found here changes that decision.

## Hot swapping (item 5)

`--smstest --only swap` (159 checks, on assembled programs and, with `--roms`, on Shinobi, Wonder Boy, GG Wonder Boy and GG Columns at frame 520). Through the session the apps build: every id of the CPU slot (Z80), the picture slot (the console's own chip and each of 13 NES chips, the SNES, three Game Boy chips and the Genesis chip drawn through the NES) and the sound slot (own unit, `SMS-FM` on the Master System, 19 NES chips) is swapped after 90 frames of a program with a steady 440 Hz tone and a scrolling picture, and 90 frames run on. After each swap the work RAM, VRAM, colour RAM, Z80 PC and cycle count equal a run with no swap (a swap never disturbs the machine), the picture is the no-swap picture pixel for pixel on the console's own chip and a real (non-blank, moving, 256 x 240) picture on a NES chip, the tone keeps the PSG's pitch within 2 percent and is audible (**NES:QLQ plays the tone an octave up and at half level on a fresh session too**, so the suite names that exception; the plugin's self-test already calls QLQ "an octave sharp on purpose"). An id off the menu (`BOGUS`, `NES:NOPE`, `MD`, `NO-SUCH-UNIT`, `SMS-FM` on the Game Gear, an empty id) is refused and nothing changes; every picture and sound id of the menus also builds a session of its own (the path the apps take when a swap cannot be done in place); chains (own unit to SMS-FM to NES:FIX to NES:FIXS and back; the picture through five chips; all three slots interleaved) and a swap of both slots on each of 60 frames. **No slot refuses a menu id: every swap is in place.** A unit that comes back from a NES chip takes over the PSG's registers but not the phase of its square waves, so its first cycle starts afresh (not sample for sample the control's, which the suite says). It found a real bug (see "What exists"). The desktop's own handling (`MainForm.SetConsoleCore`: restart the game when the session says false) was read, not driven.

## About the oracle and the tools (for whoever uses them next)

* The oracle's Lua script fails silently when a path passes 260 characters; `mesen-compare.ps1` now cuts the tag to 28 characters, and a shallow scratch folder (`C:\bn_a4`) is needed. That, not the game, is why 8 long-named games "could not be captured" in A3.
* `Start-Process -ArgumentList @(..., '-Modes', 'a=b c')` splits the value at spaces; pass a single `-Command` string.
* The oracle's start phase file now also records its VDP counter state at the first instruction: always counter 255, latch 0, no flag pending, whatever the power-on line; **but the latch of 0 makes the line counter underflow at the first picture line and leaves a line interrupt pending** (see the Shining Force II item above).
* **Mesen's test runner ends every run after exactly 100 seconds** (exit code -1; about 380 frames per second of a bare script, fewer with dumps: 26,000 to 38,000 frames), whatever the script does. A longer play is cut into runs chained through the oracle's own save states: `mesen-capture.ps1 -Segment N` (and `mesen-compare.ps1 -Segment`, `capture.lua` `MESEN_STATE_OUT` / `MESEN_STATE_IN`). A state can only be created or loaded inside an exec callback of the main CPU (the error says so), so a callback that removes itself after one instruction is registered for the moment. A chained capture equals this emulator's frames beyond the cuts (frames 100, 19,990, 21,000 and 45,000 of Shining Force II's title demo, 3 runs: identical).
* `capture.lua` walked the whole input script at every poll, which made a 2,800-entry script crawl; it keeps a position now.
* The pad flips within a frame at exactly the same Z80 cycle in the oracle and here (a probe that samples port $DC in a 47-cycle loop: three power-on lines, equal sample index of the change), so input timing is not a source of difference.
* The oracle's `emu.memType.smsCartRam` reads the cartridge RAM (32 KB).

## Decisions

* TrySwapCore refuses what the menu does not offer instead of accepting it (a silent label for the CPU slot, a unit the Game Gear lacks); the apps then restart the game, which says so.
* The oracle's Z80 lengths, R-in-HALT behaviour and the VRAM access queue stay as decided in A2 / A3 (tool settings only / not modelled): this round's scans found nothing that argues for changing them.
* A `.sms` file with a Game Gear header stays a Game Gear (Phase 0's contract test says the header decides); the oracle decides by the extension; the only affected library files are broken GG2SMS hacks.
* UAT goldens are recorded while the games are played, not at their titles; they are regression guards, not accuracy claims.
* The oracle's data port loses bytes during the picture (item 5 above); the app does not copy that until the rule is known and a test (FluBBa's VDP test and the roster) agrees: a model that loses too much would break games that write fast on purpose.
* The oracle's line counter at power-on (`OracleLineCounterAtPowerOn`) is a tool setting like `OracleZ80Timing`: the app keeps the state the real machine's BIOS leaves, which is also what the first instruction of a cartridge sees in the oracle (registers equal), except for this one flag.
